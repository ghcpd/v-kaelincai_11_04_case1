# Evaluation of GPT-5-Codex, GPT-5, Claude Sonnet 4.5, S100, and S40 on Feature & Improvement – API Change Implementation and Validation

## 📌 Overview
This repository contains two self-contained Python projects that simulate an API migration from the deprecated `/v1/user` endpoint to the modern `/v2/profile` endpoint. The work supports an experiment measuring how well AI assistants implement, refactor, and validate API changes under the **Feature & Improvement – API Change Implementation and Validation** subtype.

- **Project_A_Outdated** reproduces the legacy implementation with schema drift, token rigidity, and poor latency characteristics.
- **Project_B_Updated** delivers the refactored solution with structured responses, improved error semantics, and compatibility adapters.

Both projects ship with reproducible environments, automated tests, performance logging, and execution scripts.

## 🔁 API Change Scenario
| Aspect | `/v1/user` (Legacy) | `/v2/profile` (Updated) |
| --- | --- | --- |
| Endpoint | `Project_A_Outdated/original_api.py` | `Project_B_Updated/updated_api.py` |
| Response Schema | Flat dictionary with camel/snake case mix | Nested `user/contact/membership/activity` blocks validated with Pydantic |
| Token Handling | Single hard-coded token | Multiple migration tokens plus structured HTTP-style errors |
| Performance | Blocking sleeps per request (~45 ms) | In-memory cache & streamlined transforms (~5–7 ms) |
| Compatibility | Cannot parse nested payloads | Accepts legacy payloads while normalising to new schema |

## 🚀 Quick Start
1. Ensure Python 3.10+ is available on your system.
2. On Windows PowerShell, invoke the master script via Git Bash (installed with Git for Windows) or WSL:
   ```powershell
   bash run_all.sh
   ```
   The script creates virtual environments, installs dependencies, runs the tests for both projects, captures logs and latency metrics, and publishes `compare_report.md` at the repository root.

3. To execute projects individually:
   - **Project A (legacy)**
     ```powershell
     cd Project_A_Outdated
     bash run_original.sh
     ```
   - **Project B (modern)**
     ```powershell
     cd Project_B_Updated
     bash run_optimized.sh
     ```

## 🧪 Automated Testing & Logs
- Test suites rely on `pytest` and shared fixtures in `test_data.json` to validate schema compliance, error semantics, and performance expectations.
- Running either script rewrites the respective `log_*.txt` and `time_*.txt` artifacts with fresh diagnostics.
- Performance measurements focus on average, minimum, and maximum latency to demonstrate the improvement achieved by caching and schema alignment.

## 🔒 Environment & Reproducibility
- Each project maintains its own virtual environment folder (`.venv_original`, `.venv_optimized`) to avoid dependency clashes.
- Dependency lists live in `requirements_original.txt` and `requirements_optimized.txt`.
- The setup scripts (`setup_original.sh`, `setup_optimized.sh`) offer idempotent environment configuration.

## 📊 Reporting
Executing `run_all.sh` produces `compare_report.md`, summarising:
- Success rate across shared scenarios
- Latency deltas and peak timings
- Schema differences and compatibility notes
- Deployment recommendations

## ⚠️ Limitations
- All network interactions are simulated in-memory; no live calls are issued.
- The timing numbers rely on `time.sleep` to emulate latency and therefore illustrate relative—not absolute—performance improvements.
- Shell scripts are Bash-based. On native Windows, execute them via Git Bash, WSL, or adapt them into PowerShell equivalents.
